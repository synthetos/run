# Workspace proposal — increment 1

Status: design prototype for review, not shipping application code. This
increment stops before the SPA/session migration. This design increment changes no shipping app or safety implementation. Direction: [Workspace tenets](WORKSPACE_TENETS.md).

Increment 2 (owner review) adds workholding and stock, the tool library and
manual tool change, jog, spindle and coolant, overrides, the live job console,
the feeds and speeds advisor, new machine drawings, a minimal account menu and
firmware update and backups. Its spec and data model are in
[WORKSPACE_FEATURES.md](WORKSPACE_FEATURES.md); where it differs from this
document (for example the OD-6 labels and the Job card replacing "Next
operation"), increment 2 wins.

## The working model

One persistent shell holds one machine session. A fixed warning and machine
strip stay above every view; a labelled rail switches the working area between
Run, Configure, Machines, Projects and Analyze. The document does not scroll.
Inspectors, lists and reading panels scroll within their own regions. At
1280×720 the control strip remains fully visible. At 390 px, the rail becomes
bottom navigation and the content is a single scrolling region; this is a
preparation/inspection layout, not authorization for mobile machine control.

The selected project, the machine being edited and the connected controller
are distinct identities. Browsing or copying a different machine must never
retarget a connection. The prototype deliberately demonstrates this: copying
Shapeoko changes the library card while the persistent machine strip still
names Workshop router.

The blueprint language comes from the repository's existing tokens and
self-hosted IBM Plex fonts. Drafting grids belong to the canvas rather than
every surface. Typography, spacing and thin rules establish hierarchy; safety
colors retain their own meaning. The prototype does not change production
safety tokens. Its less dominant warning surface is a visual proposal for
review, while W1, W2 and W13 are generated byte-exact from the canonical
functions. Small-screen warning text needs particular owner/accessibility
review; no required warning may be removed to win space.

## State review and handoff

The updated prototype adds five machine-state families: disconnected,
identified/read-only, idle with a configuration difference, running/held,
and lost/orphaned. Running/held are explicit future concepts, with Pause
request feedback separate from reported state. The seven variants are selected
with the review-only header control. Unknown positions render as em dashes;
lost positions are last-known, never live.

X-min and motor proposals now persist per connector in prototype memory,
combine into one reviewable draft and can be cleared without controller effects.
See [the implementation spec](WORKSPACE_SPEC.md) for layout, components, tokens,
interaction rules and architectural acceptance criteria. The screenshot manifest
is authoritative; it covers seven states and six configuration/library/project
views at all four sizes in both themes.

## Main view designs

**Connected, idle.** Run shows the sample machine state, work and machine
coordinates side by side, WCS and offsets, source/age, homing and spindle
uncertainty. A canvas suggests the next useful action: choose an operation.
There is no false readiness, fabricated homing fact or prominent motion CTA.

**File loaded.** The same canvas shows an illustrative mounting plate. The
inspector becomes an operation summary and a review step. Source lines,
analysis and transcript have defined homes below it. There is no Arm/Start in
this read-only phase. The geometry and timing are illustrations, not interpreter
outputs; real sample files and preview integration belong to increment 3.

**Configure.** The actual TinyG v8 physical arrangement informs a newly drawn
SVG: USB at the left, input/output terminals at the top, motors 4→1 across the
bottom and power at the lower right. Clicking a connector or selecting it by
keyboard opens its inspector. Motor mechanics and switch roles are contextual,
not a page of raw firmware fields. The public reference is the
[Connecting TinyG drawing](https://github.com/synthetos/TinyG/wiki/Connecting-TinyG).
This is a layout study, not a verified pinout: exact hardware-revision matching,
individual pin hotspots and checked board-definition mapping are increment 4.
No private hardware source or image was used or copied into the prototype.

**Machines.** A private fleet sits above a catalogue. Copying a template creates
a private machine draft with a new identity, not a connection and not inherited
commissioning facts. The example cards have no executable preset values;
“source review pending” is intentional. X-Carve, Shapeoko and 3040/6040 names
alone do not identify a controller, screw pitch, electrical system or safe
travel envelope. Start with a small, reviewed catalogue and a strong Custom
machine path rather than fabricated comprehensive coverage.

**Projects.** A project groups immutable file versions, ordered operations,
tool notes and history. Each operation is reviewed and armed separately.
History is evidence, never a resumable machine session. The account panel
explains future sync without claiming that cloud saving exists today. Example
copy/create interactions are memory-only and reset on reload.

## Visual configuration and its data contract

Keep the existing separation of board capabilities, dialect settings and user
machine mechanics. A versioned presentation map binds SVG hotspot IDs to
connector IDs in a reviewed board definition. Hardware selection uses the
actual family/hp/hv match; an unknown revision gets an explicit unverified view.
The renderer does not hard-code four motors, one motor per axis or TinyG-only
setting names. g2 boards and external drivers can supply different maps.

Show function and polarity controls only where the board/dialect supports them.
TinyG's shared switch type must show its effect across all inputs. Motor frame
size does not establish rated current. TinyG current adjustment is physical;
there must be no software slider pretending to adjust a trimpot. Derive travel
per revolution from explicit mechanics and show the arithmetic. Keep board
values, unread values and draft values separate. A draft change creates a
reviewable diff; the later write pipeline retains all per-key and typed
confirmations and fact invalidations. Configuration drawing is not electrical
verification, and an E-stop drawn in a diagram does not certify the machine.

OD-5 approves a separately authored, publishable, real-looking TinyG board
illustration, v8 first. That is the configurator direction: a clean interactive
board drawing in the spirit of the Connecting TinyG images. The prototype
already uses this approach. Approval of the approach is settled; revision and
pin accuracy still require verification before the art becomes wiring guidance.
D26 still limits private-hardware inputs to derived connector positions, labels
and orientation. Never publish CAD, netlists, layout exports, private screenshots
or paths. Record the reviewed public facts shown by each illustration, and keep
detailed private extraction evidence private.

## Machine library, versions and sharing

Separate catalogue template, user machine profile, live controller snapshot
and local commissioning evidence. Templates carry a source, mechanical revision,
controller compatibility and a version for each reviewed configuration. User
forks pin the starting version. Updates offer a three-way comparison; they
never overwrite customization or board settings. Profile rollback makes a new
revision. The default drift resolution remains “keep the board's settings.”

Cloud synchronization can store profiles, wiring, projects and history. It
cannot import homing, local safety facts, confirmations or permission to resume.
D20 keeps v1 private. Later sharing is an explicit copy/import with provenance
and facts stripped, not a remotely trusted machine profile. Offline local
preparation remains useful; that does not waive D1 for new machine actions.

## Contextual controls without weaker safety

The state strip reports controller knowledge; delivery feedback reports a
request. They are not the same state. On a freshly idle machine, the strip stays
“Machine idle” when Pause is pressed, with a brief factual delivery result. It
must not become a persistent “Pause requested” pseudo-state or claim HELD without
evidence. In the static prototype, the response explicitly says it is a demo
and no motion changed.

Stop and Pause stay in fixed positions and remain usable whenever the port is
open, including idle, READ_ONLY, UNKNOWN, STALE, FAULT and ORPHANED_MOTION. This
is required by SAFETY §4.1. They become visually more prominent for motion,
hold or uncertainty; absence of a host-owned job does not establish absence of
motion. Preserve exact W2 wording. Escape remains a capture-phase stop-class
request even inside a dialog. Requests still reach all LIVE machines per the
existing cross-tab policy, with per-machine outcomes. No modal, sign-in flow,
route transition or rendering failure may cover or gate the controls.

## SPA architecture for increment 2

Replace separate runtime page entries with a document-lifetime session owner
above routed views. It owns the existing worker, RPC and live snapshots;
unmounting a view removes only that view's subscriptions. A root safety region
and early stop dispatch are independent of route rendering and lazy loading.
Navigation, Back/Forward and deep-link view changes never reopen the port or
repeat the handshake. Browsing machines does not change the session target.

Use an explicit route table and literal lazy imports. Cold links to recognized
app routes serve the app shell; missing assets remain real 404s, API/auth routes
retain their behavior, and unknown paths are handled explicitly. Direct /safety/
visits remain prerendered and readable without JS; in-app Safety uses the same
content inside the persistent shell. Refresh, tab closure and browser failure
remain connection-loss cases: no URL or saved route restores authority or a job.

Keep current CSP/Trusted Types constraints, initialize policies once, and render
with DOM/components rather than HTML fragments. Keep the chooser's approved
page boundary and transport's worker boundary. Scan lazy chunks and preserve
fake/release and bench/release comparisons. Production serial denial remains.
Never force a LIVE tab to reload for updates, authentication or missing route
chunks. Retain older assets for long-lived tabs. This work intentionally changes
P0-01's MPA implementation; the preserved guarantees need explicit regression
coverage before it replaces the current entry points.

## Analysis, generation and differentiation

Analyze shares the operation and geometry with Run. Selecting a finding should
reveal the associated source lines and spatial location. Show estimates as
estimates and separate them from validated safety bounds. Generation produces
an immutable candidate file; optimization offers before/after comparison and
new sanitizer/preflight/approval. Neither may rewrite an armed stream. Heavy
work stays outside the stop path with explicit resource limits; predicted
position never masquerades as measured position.

The product goal is continuity from recognizable board to understandable setup
to reviewed operation and honest recovery. The published products offer useful
reference strengths: [gSender](https://sienci.com/gsender/) emphasizes usability
and calibration, [CNCjs](https://cnc.js.org/) customizable browser control,
[UGS](https://winder.github.io/ugs_website/) visualization and design tools,
[ChiliPeppr](https://github.com/chilipeppr/workspace-tinyg) composable TinyG
workspaces, and [Easel](https://www.inventables.com/pages/easel) a design-to-cut
journey. These are reference directions, not a tested superiority claim.
Measure success through user tasks: recognize the connected machine, configure
a switch correctly, resolve drift, prepare an operation, and identify a lost
connection without confusing it with a stopped machine.

## Review boundary

The two open Phase 1 safety findings remain independent: port selection by
grant index/VID/PID can identify the wrong board when the list changes, and the
garbled initial-answer branch still retries without trustworthy `sr` evidence.
This visual prototype does not fix or hide either finding.

Increment 1 asks for review of hierarchy, navigation, density, safety prominence,
board interaction and narrow-screen behavior. It does not claim 60 fps geometry,
validated catalogue presets, cloud persistence, worker persistence or working
configuration writes. Those are later increments, each independently reviewed.
